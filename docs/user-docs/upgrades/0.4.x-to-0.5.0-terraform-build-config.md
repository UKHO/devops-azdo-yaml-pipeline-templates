# Upgrade Guide: 0.4.x → 0.5.0 - Build Parameters → TerraformBuildConfig

This guide shows how to move the Terraform build settings from top-level parameters into the new `TerraformBuildConfig` object. The old parameters still work until the next major release, so you can upgrade when it suits you, but new features such as [Build Checks](../checks/README.md) are only available in `TerraformBuildConfig`.

## Upgrade Path

Move each build setting under `TerraformBuildConfig`, keeping its value. `TerraformBuildInjectionSteps` is the only one that is renamed:

- `ArtifactName` → `TerraformBuildConfig.ArtifactName`
- `TerraformVersion` → `TerraformBuildConfig.TerraformVersion`
- `RelativePathToTerraformFiles` → `TerraformBuildConfig.RelativePathToTerraformFiles`
- `AdditionalFilesToPackage` → `TerraformBuildConfig.AdditionalFilesToPackage`
- `TerraformBuildInjectionSteps` → `TerraformBuildConfig.InjectionSteps`

`Condition`, `DependsOn` and `Pool` stay where they are.

### Terraform Build Job

Before:

```yaml
- template: jobs/terraform_build.yml
  parameters:
    ArtifactName: MyArtifact
    TerraformVersion: 1.14.0
    RelativePathToTerraformFiles: infra
    TerraformBuildInjectionSteps:
      - pwsh: Write-Host "Preparing..."
```

After:

```yaml
- template: jobs/terraform_build.yml
  parameters:
    TerraformBuildConfig:
      ArtifactName: MyArtifact
      TerraformVersion: 1.14.0
      RelativePathToTerraformFiles: infra
      InjectionSteps:
        - pwsh: Write-Host "Preparing..."
```

### Terraform Pipeline

The pipeline's `TerraformVersion` stays a top-level parameter, because it is shared by the build and deploy stages. `ArtifactName` is not available, because the deploy stages always use the artifact `TerraformArtifact`.

Before:

```yaml
extends:
  template: pipelines/terraform_pipeline.yml
  parameters:
    TerraformVersion: 1.14.0
    RelativePathToTerraformFiles: infra
    EnvironmentConfigs: [...]
```

After:

```yaml
extends:
  template: pipelines/terraform_pipeline.yml
  parameters:
    TerraformVersion: 1.14.0
    TerraformBuildConfig:
      RelativePathToTerraformFiles: infra
    EnvironmentConfigs: [...]
```

## Coexistence Rule

A setting can't be given both as a deprecated parameter and in `TerraformBuildConfig`; the pipeline fails to compile with a message naming the setting. You can move settings across one at a time: a deprecated parameter and a *different* `TerraformBuildConfig` field can be used together.

## What Changed

- The build settings live in one object, validated when the pipeline compiles: misspelled or unknown fields, and `AdditionalFilesToPackage` entries missing `SourceDirectory` or `FilesPattern`, are now reported clearly instead of failing later or being ignored.
- Each deprecated parameter still in use logs a warning on the run, in a `DeprecatedParametersWarning` step at the end of the build job. Warnings don't change the run's result.
- A deprecated parameter set to its default value can't be detected, so it doesn't log a warning; it also has no effect, so you can simply delete it.
- `InjectionSteps` is checked for being a list when the pipeline compiles; the steps themselves are checked when they are inserted, so an invalid step gives Azure DevOps's own error message rather than one naming `InjectionSteps`.
